# 短剧生产标准流程（Agent 骨架 → Gemini4 重写 → Agent 规范）

> **2026-10-18 固化**。这是本技能唯一认可的生产流程，不要用「一次性交给 LLM 生成全部」的替代做法。
>
> 核心分工：**结构由 Agent 保证，文采由 Gemini4 提升，最终质量由 Agent 把关**。

---

## 总览

```
① Agent 用山音九列规范搭骨架
        ↓
② Agent 做逻辑自检（必做，不通过不进下一步）
        ↓
③ Gemini4 重写（只调一次；超时按输出字数动态 120–300s；失败降档；再失败 Agent 自润）
        ↓
④ Agent 规范化为成果（验收 + 格式化输出）
```

**为什么这样分工**：
- 山音九列是**确定性结构**（列名固定、规则明确）→ Agent 直接写最快最准，不需要 LLM 生成
- Gemini4 擅长**语言润色与参数补充**（把"温馨日常"扩写成色温/焦段/推速）
- 最终必须由 Agent **验收**，因为 Gemini4 会自由发挥、漏镜、改时长

---

## Step 1：Agent 用山音九列规范搭骨架

**输入**：剧本 / 文字脚本
**执行者**：Agent 本人（不调 LLM）
**输出**：骨架 Markdown，包含四部分

1. 导演定调（六维判断 + 七项视听决策 + 意象体系）
2. 节奏规划（双轨节奏 + 时长分配表）
3. 九列分镜表（镜号 | 时长 | 摄影角度 | 景别 | 画面内容 | 场景 | 声音 | 备注 | 叙事目的）
4. 生成任务划分（4–15 秒/任务，总和 = 目标时长）

**写骨架的硬规则**：

- 镜号连续，最后一镜时长写「结束」
- 摄影角度只允许：平视、俯拍、微俯拍、仰拍、低机位
- 景别只允许：远景、全景、中远景、中景、中近景、近景、特写、大特写
- 画面内容只写摄影机拍得到的动作与物体（不写心理、不写括号暗示）
- 声音列只写：对白（角色：台词）/ 环境声 / 静音
- 叙事目的用客观分析语气，具体到视听手段
- **时长按台词字数算**：中文口语约 5 字/秒，台词密集段单镜压到 1–2 秒
- 分镜总数与任务数的换算：**单任务 4–15 秒**，一个任务通常装 2–6 镜

**骨架产物命名**：`00-骨架.md`

## Step 2：逻辑自检（必做，不可跳过）

骨架写完**先自己查一遍**，发现问题就地改，**不通过不进入 Step 3**。

### 必查清单

| # | 检查项 | 典型问题 |
|---|---|---|
| 1 | 台词有对象 | 「孩子对着水面喊」→ 无对象 |
| 2 | 台词有视线 | 「妈妈头也没回地说」→ 视线缺失 |
| 3 | 台词与动作因果顺序 | 「接过球拍说：给我一个球拍」→ 顺序颠倒 |
| 4 | 台词回答有人问过的问题 | 「不是来打球的」却没有邀请者 |
| 5 | 动线连续 | 分开后又回来道别 / 孩子凭空消失 |
| 6 | 孩子监护 | 妈妈独处时孩子必须有交代（画外声或交接） |
| 7 | 站位明确 | 球台必须写「各站一端隔网面对面」 |
| 8 | 道具状态连贯 | 球拍数量、归属、递接顺序 |
| 9 | 服装一致 | 同一角色全片服装不跳变（换装要有交代） |
| 10 | 时长合计 | 各任务时长之和 = 目标总时长 |
| 11 | 反常识 | 高跟鞋踩泳池边、毛巾入水、跑步机朝向反 |
| 12 | 叙事递进 | 把任意两场交换，故事还成立吗？成立 = 并列，需重排 |

**自检发现问题时，直接改骨架**，并把改了什么记在骨架末尾的「自检记录」里（供 Step 4 验收对照）。

## Step 3：Gemini4 重写（只调一次，超时按字数动态计算）

### 档位选择（按产出类型，2026-10-18 调整）

**thinking-high 太慢**（实测 77s/817字、188s/11513字），只用于关键文本；结构化输出用基础档。

| 产出类型 | `kind` | 档位 | 理由 |
|---|---|---|---|
| 剧本创作 / 剧本重写 | script | **thinking-high** | 台词逻辑、结构、情感，最关键的文本 |
| 执行脚本重写（分镜表） | script | **thinking-high** | 60 镜结构 + 专业参数，一次成型的核心产物 |
| 导演定调方案 | script | **thinking-high** | 视听决策判断 |
| 即梦提示词 | prompt | **基础档**（`gemini-4-argon`） | 10 区块模板化填写，结构化程度高，速度快 10–20 倍 |
| 营销文案 | copy | **基础档** | 短文本，模板感强 |
| 文章 | article | **基础档** | 结构清晰 |
| 故事 | story | 长文 high / 短文 base | 按篇幅判断 |

**判断标准一句话**：**要「想」的（逻辑/结构/情感）用 thinking-high；要「填」的（模板/区块）用基础档。**

**成本对比**：think-high 单次 77–188 秒；基础档单次 4–12 秒（几百字）到 30–60 秒（长文）。

### 超时公式（2026-10-18 实测拟合）

> **等待时长与输出字数近似成正比**。固定 180s 对 1 万字以上的任务不够（实测 11513 字耗时 188s，
> 已超过 180s），对短任务又是浪费。因此按预期输出字数动态计算。

```
预估输出字数 W ≈ 骨架字数 × 1.5~2.0
（也可按任务类型估：60 镜的分镜表约 10000–12000 字）

thinking-high 超时 = clamp(70 + W × 0.012, 120, 300) 秒
基础档超时        = clamp(40 + W × 0.006,  60, 150) 秒
```

**实测校准数据**（gemini-4-argon-thinking-high）：

| 输出字数 | 实测耗时 |
|---|---|
| 817 | 77s |
| 2097 | 101s |
| 11513 | 188s |

**参照表**：

| 预期输出 | thinking-high 超时 | 基础档超时 |
|---|---|---|
| ≤ 2000 字 | 120s | 60s |
| 2000–5000 字 | 120–150s | 60–80s |
| 5000–8000 字 | 150–180s | 80–100s |
| 8000–12000 字 | 180–240s | 100–130s |
| > 12000 字 | 240–300s | 130–150s |

**上限 300 秒**：超过 300s 说明单次任务太大。此时要么把骨架拆细后仍只调一次，
要么直接由 Agent 自己润色（不要为了等结果无限延长）。

### 调用规则（不可变）

```
第 1 次：gemini-4-argon-thinking-high，超时 = 动态值（见上表）
第 2 次：gemini-4-argon（基础档），超时 = 动态值     ← 仅当第 1 次失败
第 3 步：都失败 → Agent 自己润色（不报错、不重试、不再调 LLM）
```

**硬性约束**：
- **整套流程只调用 Gemini4 一次成功**（第 1 次成功就不再调；第 1 次失败才允许第 2 次）
- 每档**只尝试一次**，不重试
- 超时到点即放弃该档
- 任一次拿到非空文本就停止，进入 Step 4
- 全部失败时**不抛错**，由 Agent 基于骨架自己润色（骨架本身已经是完整产物）

### brief 模板

```
请基于下面这份骨架，重写成一份正式的短剧拍摄执行脚本。

【项目】<片名>，<类型>，总时长 <N> 秒，<场数> 场。

【重写要求】
1. 导演定调：把骨架判断扩写成专业表述，给出具体可执行参数
   （镜头焦段/机位/推速、色温区间、光位、景深、配色配比、平均镜头长度）
2. 节奏规划：逐场双轨节奏 + 镜头组划分（蒙太奇组/递进组/因果组/对比组）+ 节奏诊断
3. 九列分镜表：在骨架基础上精修措辞，保持镜数与总时长，规则同骨架
4. 生成任务划分：<N> 个任务，每个 4-15 秒，总和 = 目标时长

用 Markdown 表格。不写心理描写、不用括号暗示、不用 Markdown 加粗。
```

**context 必带**：剧本全文 + 骨架全文。

### 调用实现（comfly 直连）

- Endpoint：`https://ai.comfly.org/v1/chat/completions`
- Key：`.credentials.yaml` 里的 `COMFLY_API_KEY`
- `max_tokens: 32768`（thinking 变体先耗思考 token，给少了会截断成空回复）
- 网络抖动时**只在同一档内切换直连/代理一次**，不叠加长重试链
- 长任务用**后台 job**，避免阻塞对话

### 失败判定

以下任一情况算该档失败，进入下一档：
- HTTP 错误（含 SSL 中断）
- 超时到点
- 返回文本为空 / 长度 < 500 字符（视为无效）

## Step 3.5：提示词的分块生成（2026-10-18 优化，写即梦提示词时必用）

**不要一次性让 Gemini4 写完 N 段提示词**。9 段一次生成实测两次都 SSL 断连（请求太大）。

### 分块规则

| 区块 | 谁负责 | 调用次数 |
|---|---|---|
| 【布光锁定】 | **Gemini4 单独 1 次** | 1 次（整片共用） |
| 【故事背景】+【画面内容】+【镜头】 | **Gemini4 每段 1 次** | N 次（可批量并行） |
| 其余 7 个区块 | **Agent 拼装** | 0 次 |

### 必须给 Gemini4 看视觉参考（2026-10-18 补，关键）

**只给文字（"客厅""大堂"）是错的** —— 她会凭空想象场景与人物，写出来的提示词和真实素材对不上。

**每段 brief 必须附图片**。comfly 的 `gemini-4-argon` **支持 vision**（OpenAI 兼容 `image_url` + data URI），已实测通过。

| 附什么 | 说明 |
|---|---|
| **场景图**（1 张） | 该段对应的场景卡，让她知道空间、家具、材质、配色、光线 |
| **角色卡**（按出场） | 每个出场角色的角色卡，让她知道长相与服装 |
| **比例参考**（同框段） | 全家福比例参考，约束三人身高体态 |

**图片处理**：Pillow 压到长边 **1024px**、JPEG **q85**、base64 约 **140KB/张**；9 段并发 3 时稳定。

**效果对比**（同一段 T01）：

- ❌ 无图：「阳光洒满客厅……妈妈正低头整理手提包」（泛泛而谈，和真实场景无关）
- ✅ 有图：「清晨暖阳透过大落地窗洒满米色调的宽敞客厅。妈妈站在**白色弧形沙发**与后方**木质书桌**过道旁……爸爸站在**原木圆茶几**旁……孩子从**左侧大理石壁炉**旁跑过来」（贴合真实场景图）

### 核心原则：创意大自由度，**但台词要基本尊重原稿**

**剧本是草稿，但不是废稿**。要给足创意空间，同时守住两条线：

| 项 | 自由度 |
|---|---|
| **台词** | **必须基本保留**（用户确认过的内容不能改），只允许**微调措辞**让它更口语、更自然，不得增删台词或改变意思 |
| **动作** | 可以自由丰富、调整、替换，让画面更生动 |
| **镜头**（景别/机位/焦段/运镜/切镜） | **完全自由**，由她的专业判断决定 |
| **节奏** | 段内快慢可自由安排 |

**必须给的硬约束**（因为技术上必须）：

- 这一段**多长时间**
- 这一段**必须发生什么**（一句话剧情节点）
- **角色是谁、穿什么**
- **台词清单**（原文照录，标注"只能微调措辞"）
- 极少数**物理约束**（如「全段只有爸爸和妈妈手里有球拍」）

### 批量提交

**N 个段落任务并行提交**，不要串行等待。每段输出约 400–900 字：

- 基础档超时：`clamp(40 + W×0.006, 60, 90)` 秒
- **并发上限 3**（实测并发 9 会被拒）
- **必须用 curl 发请求**：urllib 的 SSL 栈处理长响应会 `UNEXPECTED_EOF_WHILE_READING`（小请求能通、长响应必挂）
- 任一失败 → 该段用 Agent 兜底（不重试、不阻塞其他段）

### brief 模板（每段一次）

```
这是这一场戏的草稿。

【场景】<场次>  <场景名>  <时长>s
【人物】<角色 + 服装>
【这一段必须发生的事】<一句话剧情节点>

【台词】（必须基本保留，只能微调措辞让它更口语化，不要增删或改变意思）
- <角色>：「<原台词>」
- …

【动作与镜头】（你可以自由设计、丰富、重写）
<原分镜动作，仅作参考>

【输出】
【故事背景】一句话，谁在哪做什么
【画面内容】动作 + 台词 + 视线（台词按上面的清单，措辞可微调）
【镜头】景别 / 机位 / 焦段 / 运镜（你自由设计）

不要 Markdown、不要解释、不要加粗。
```

### 布光锁定 brief 模板（整片一次）

```
为一部 <类型> 短剧写即梦提示词的【布光锁定】段落（整片 N 段共用一条）。

【风格基调】<温馨日常 / 建发高端 / 日系青春 …>
【色彩倾向】<暖金奶油 / 香槟象牙 …>
【光位】<自然窗光 / 纱帘逆光 / 灯槽擦墙 …>
【要求】英文，8 维度齐全：影调坐标 / 质感 / 光学 / 调色 / 曝光 / 运动 / 情绪 / 声源。
只输出这一段英文，不要解释。
```

### 拼装顺序（Agent，不调 LLM）

```
【风格】固定一句
【布光锁定】← Step 3.5-A 产出（N 段逐字相同）
【参考】← 素材节点 {{node:xxx}} + 「只取材质光线」说明 + 比例参考说明（同框段）
【设定】固定（语言 + 表演基调；无台词段改写）
【特殊要求】按场景类型选（私密=绝对无人 / 公共=1–3 位成年住户）
【导演】固定
【故事背景】← Step 3.5-B 产出
【画面内容】← Step 3.5-B 产出
【镜头】← Step 3.5-B 产出（含景别/机位/焦段/运镜，已按全局镜头约束优化）
【一致性】模板 + 本段角色服装锁定 + 本段特有约束（球拍数量/唯一孩子/不露正脸等）
【限定】固定
```

### 验收（拼装后必查）

- N 段提示词的【布光锁定】必须**逐字相同**
- 每段的 `{{node:xxx}}` 引用数量与 refs 列表**完全一致**（多一个少一个都会让平台报 `invalid_input`）
- 角色服装锁定与执行脚本一致
- 无 Markdown 标记、无占位符残留（`图片N`/`音频N`）

### 硬规则汇总（通用版，2026-10-19 从实战提炼）

> 以下规则**去掉了项目定制**，可迁移到任意短剧 / 剧情 TVC 项目。
> 每条附「为什么」——那是踩过的坑，不是理论。

#### A. 输入与参考

| # | 规则 | 为什么 |
|---|---|---|
| A1 | **必须给生成模型看视觉参考**（场景图 + 角色卡） | 只给文字（"客厅""大堂"），模型会凭空想象，提示词和真实素材对不上 |
| A2 | **参考素材仅为场景参考** | 参考图提供长相/服装/材质/光线，只作参考，不直接复用其视角与构图 |
| A3 | **背景人物必须另行描述且与主角明显区分** | 模型会把主角的角色卡形象**优先套用给路人**。参考图不是背景角色库；背景人物长相/发型/服装必须完全不同，无法区分时宁可不出现 |

#### B. 结构

| # | 规则 | 为什么 |
|---|---|---|
| B1 | **单任务运动可控：2–4 个切点明确的镜头** | 7–15 秒内做多景别 + 多人走位，生成模型必崩。避免在一个任务里连续跨景别/机位运动 |
| B2 | **区块职责清晰** | 【画面内容】= 连续画面流（不写镜头编号）；镜头编号只在【镜头】；有台词/无台词段分别对待，不能照抄模板（挂了音频参考 ≠ 有台词） |
| B3 | **连续性强的前后段合并成一次调用** | 动作、道具、服装跨段连续时（湿发状态、球拍归属、换装前后），合并生成才能保证状态传递 |

#### C. 描述方式

| # | 规则 | 为什么 |
|---|---|---|
| C1 | **只写可见结果** | 只写摄影机拍得到的东西；专业动作（球类/器械/技艺）写"在做什么"而非分解动作——分解动作会让模型误判 |
| C2 | **用正面描述代替否定指令** | 不写"不要看镜头""不要摆拍"——视频模型会把否定句当成画面内容，实测触发 `errorCode 20010` 稳定失败。想表达"自然"就直接描述自然状态 |
| C3 | **不写后期内容** | 字幕、logo、水印、转场特效属于后期，不写进生成提示词 |

#### D. 一致性

| # | 规则 | 为什么 |
|---|---|---|
| D1 | **单一事实源** | 脚本、提示词、画板节点任何一处改动，必须同步其余两处——否则后面自相矛盾 |
| D2 | **台词尊重原稿** | 台词是用户确认过的内容，只允许微调措辞，不得增删或改意思 |

#### E. 技术事实

| # | 规则 | 为什么 |
|---|---|---|
| E1 | **必须用 curl 发请求** | urllib 的 SSL 栈处理长响应会 `UNEXPECTED_EOF_WHILE_READING`（小请求能通、长响应必挂） |
| E2 | **并发 ≤ 3** | 实测并发 9 会被服务端拒绝 |
| E3 | **图片压到长边 1024px / JPEG q85** | base64 约 140KB/张，请求体积可控 |
| E4 | **拼装后校验 node 引用数 == refs 数** | 多一个少一个都会 `invalid_input`（曾因一个字符差异排查很久） |
| E5 | **单段时长 ≤ 模型上限** | 先查 `catalog list --type video`，超了报 `FIELD_VALUE_INVALID` |
| E6 | **docx 必须设 `w:eastAsia`** | 否则 Word 打开中文乱码（见 Step 4） |

## Step 4：Agent 规范化为成果

**Gemini4 的输出必须验收**，不能直接交付。

### 验收清单

| # | 检查项 | 处理 |
|---|---|---|
| 1 | 镜号连续且数量与骨架一致（±2 镜内） | 缺镜/多镜 → 以骨架为准补齐或删除 |
| 2 | 各任务时长之和 = 目标总时长 | 不符 → 按骨架时长表修正 |
| 3 | 是否出现骨架里没有的镜头/台词 | 出现 → 以骨架为准删除 |
| 4 | 是否漏掉自检时修正的漏洞 | 漏 → 按「自检记录」补回 |
| 5 | 格式合规（九列齐全、角度/景别用标准词） | 违规 → 替换为标准词 |
| 6 | 是否混入 Markdown 加粗/括号暗示/心理描写 | 有 → 清除 |
| 7 | 生成任务与镜号的对应关系是否连续 | 断档 → 重排 |

### 格式化输出

- 保存 `.md`（可编辑）与 `.docx`（交付）
- Markdown 表格转 docx 时用真表格（`docx.add_table` + `Table Grid`），不要拍平成纯文本
- 文件命名：`01-执行脚本-正式版.md` / `.docx`
- 骨架保留为 `00-骨架.md`，作为可追溯的输入

### docx 必须设东亚字体（否则中文乱码）

**踩过的坑（2026-10-18）**：python-docx 的 `font.name` 只设西文字体（`w:ascii` / `w:hAnsi`），
**不设 `w:eastAsia`**。Word 打开时中文走默认字体渲染，破折号（——）、间隔号（·）、® 等
特殊标点直接变方框 —— 用户反馈「有无法识别的文字」。

正确做法：**样式 + 每个 run（含表格单元格）都设四组字体属性**。

```python
from docx.oxml.ns import qn

FONT = "Microsoft YaHei"

def force_font(el):                    # el = style.element 或 run._element
    rpr = el.get_or_add_rPr()
    rfonts = rpr.get_or_add_rFonts()
    rfonts.set(qn("w:ascii"), FONT)
    rfonts.set(qn("w:hAnsi"), FONT)
    rfonts.set(qn("w:eastAsia"), FONT)   # ← 中文靠这个
    rfonts.set(qn("w:cs"), FONT)
```

必须覆盖：`Normal`、`Heading 1~3` 样式 + 每个段落 run + **每个表格单元格 run**。

**生成后必须验证**（不能只看文本对不对）：

```python
# 遍历所有表格 run：有文本的 run 的 eastAsia 必须等于 FONT，期望缺字体数 == 0
bad = 0
for t in doc.tables:
    for row in t.rows:
        for c in row.cells:
            for p in c.paragraphs:
                for r in p.runs:
                    if r.text.strip() and r._element.rPr.rFonts.get(qn("w:eastAsia")) != FONT:
                        bad += 1
```

经验值：60 镜的执行脚本约 **1500 个表格 run**，全部要有字体。
另外：Markdown 的 `---` 分隔线不要原样写进 docx（会出现一行无意义的「---」），转换时跳过。

## 常见错误（都是踩过的）

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 直接把剧本丢给 LLM 生成分镜 | 结构散、漏镜、台词逻辑不查 | 先出骨架，再润色 |
| Gemini4 输出直接交付 | 偏离骨架、时长对不上 | Step 4 必须验收 |
| 长重试链（多次 × 长超时） | 对话卡死十几分钟 | 每档只试一次，硬超时 |
| 用「二选一」而不是「线性」 | 骨架的价值被浪费 | 骨架是输入，不是备选 |
| 自检跳过 | 逻辑漏洞带进成品 | Step 2 必做 |
